# Backlog providers

Maintainer guide to this folder. No agent reads it.

- `CONTRACT.md`: the provider contract every skill speaks (verbs, six states, exit codes, claim rules). Skills read it.
- `local.md`: the default file-based backlog, prompt-implemented.
- `wa-backlog`: the one backlog script every shared board uses (Python 3 stdlib plus `gh`, one file, vendored by projects as `.github/board/wa-backlog`). A shared core (CLI, verbs, claims as git refs on GitHub, ticket branches and task phases, pull requests, merge, stacks, screenshots, the contract check, `hook`, `migrate`) plus one `Board` adapter per board tool: `GitHubBoard` and `PlaneBoard`.
- `github/`: the GitHub Project board. `github/wa-backlog` is a relative link to `../wa-backlog`, kept because skills, the pane and `/wa-setup`'s vendored copy use that path (`cp` follows the link, so projects get a real file). Its hooks are `.github/workflows/board.yml` (JavaScript), called through `github/whackagent-board.yml`.
- `plane/`: the Plane CE board (experimental). Its hooks are `wa-backlog hook`, run by `.github/workflows/board-plane.yml` on a self-hosted runner, called through `plane/whackagent-board-plane.yml`.

## Adding a board tool

The board and the code host are two separate choices (`backlog.provider`, `vcs.provider`). Code stays on GitHub: claims, branches and PRs are the shared core's and need nothing from the board. A new board tool (Linear, Jira, OpenProject, Vikunja…) is therefore one adapter class, its hooks, and the text around them. The Plane provider is the worked example for every step below; its README records how each one was answered.

1. **Check the tool can hold the contract.** Through its API, it must create or adopt columns with custom names (the six states plus a canceled one), keep one stable card order that both the UI and the API read, take comments, and let the adapter find cards by a stable id. Labels (for `wa-ignore` and sprint roots), parent cards (sprints), some release grouping (milestones), "blocked by" relations and assignees (reservations) are each needed for the matching verb; a missing one makes that verb exit 2 with a clear message. Its own GitHub sync must be switchable off: the hooks are the only writer of the data-driven states. Check rate limits and whether the free or self-hosted edition exposes what you need, and record every fact with its evidence, as `plane/README.md` → *Verified API facts* does.
2. **Write the adapter.** A `Board` subclass in `wa-backlog`, registered in `BOARDS` under its `backlog.provider` name. The module docstring at the top of the script is the authoritative interface: the ticket dict every method returns, and every operation grouped by reading, writing, milestones, sprints and the rest. Override what the tool supports; an operation it has no meaning for keeps the base method, which exits 2. `check_id` refuses an id of the wrong shape before any call (`12` on a key-based board), and ticket ids are opaque everywhere else, so the skills, the pane and the claim refs need no change for a new id shape. Keep the script stdlib only and in one file: projects vendor it as is.
3. **Settings.** `settings(repo, variables)` resolves the board's ids from repository variables (`WA_<TOOL>_…`) and the core caches them per clone. In Actions the script reads the variables from `WA_VARS`, because `GITHUB_TOKEN` cannot list them. The tool's API token comes from an environment variable for agents and an Actions secret for the hooks, never from the repository or the config.
4. **Provision and the single-writer guard.** `provision` adopts an existing project (never creates one), creates or maps the states by name (`--state`), never renames or deletes a column unless the user names it (`--prune-status`), writes the variables, and is idempotent. `check_integration` answers whether the tool's own GitHub sync is off, so setup can stop while it is on.
5. **Hooks.** A board other than a GitHub Project must be moved from GitHub events. `wa-backlog hook` reads the event from the Actions environment and dispatches it through `HOOKS` (`push` → `hook_push`, `pull_request` → `hook_pull_request`, `schedule` and `workflow_dispatch` → `hook_check`). These handlers hold the rules of `board.yml` and were written against `PlaneBoard`: beyond the interface they call its helpers `base`, `api`, `key`, `item`, `board_items`, `is_root`, `links`, `linked_prs`, `linked_tickets`, `sprint_parent`, `sprint_complete`, `open_sprint` and `close_sprint`. A second tool implements the same helpers, or lifts them into the interface; keep the hook rules themselves identical, since `BOARD.md` promises the same behavior on every tool. Ship a reusable workflow `.github/workflows/board-<tool>.yml` (copy `board-plane.yml`: only its settings check and secret name are Plane's) under the `hooks-v2` tag, and a caller template `providers/<tool>/whackagent-board-<tool>.yml` with its own `template version`. Decide where it runs: a self-hosted runner when the tool sits on a private network, GitHub-hosted otherwise.
6. **The board contract.** Add a `<!-- board-tool: <tool> -->` block with a `## This board: <Tool>` section to `templates/BOARD.md`, and the matching blocks to `templates/pr-board-sections.md`. The shared rules stay identical for every tool; only change them (and bump `board-contract` everywhere plus `CONTRACT_VERSION`) when the rule really changes for all boards.
7. **The skill side.** A caveman-style `reference/board-<tool>.md` with the board part of the rules (the code-host part is `reference/code-github.md`, shared), added to the `Read` line of every skill that loads `board-plane.md`, with the condition `backlog.provider: <tool>`. A row in the providers table of `CONTRACT.md`, an entry in `reference/provider.md`, the value in `templates/config.md`, and a `<Tool> backlog` section in `/wa-setup` (where, token, integration check, provision, hooks, setup PR), plus a switch section if projects can migrate to it.
8. **Docs.** `providers/<tool>/README.md` (mapping, settings, hooks, verified facts, footprint for a self-hosted tool), a section in `README.md`, a walkthrough next to `GITHUB.md` and `PLANE.md`, the differences in `WORKFLOW.md`, and a `CHANGELOG.md` line marked experimental.
9. **Test against a real tracker.** A local instance or a test workspace plus a private playground repository, never a real project: check `gh api repos/<repo> --jq .full_name` before any live write. Run every verb and check the board with `get` and `list`; race six parallel claims for exactly one winner; replay the hooks with recorded payloads (`wa-backlog hook --event <name> --payload <file>`), then end to end with real pushes and PRs; run the GitHub playground scenarios again to prove the GitHub board did not change. `scripts/plane-rig/` shows the Plane version of this setup.
